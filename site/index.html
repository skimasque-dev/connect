GitHub Action · skimasque-dev/connect

One step gives the job policy-controlled private access.

connect opens an identity-bound MASQUE tunnel for the rest of a CI job. It trades the runner's OIDC token for a renewable credential. On supported dedicated Ubuntu runners, configured private TCP, UDP and DNS use the gateway, even when tools ignore proxy variables. Public traffic keeps its normal route. Other runners can select explicit HTTP/SOCKS proxy mode.

Add it to a workflow → View on GitHub
.github/workflows/deploy.yml
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write        # required
      contents: read
    steps:
      - uses: skimasque-dev/connect@v1
        with:
          proxy: gateway.example.com:443
          audience: https://gateway.example.com
          application: terraform
          routes: 10.42.0.0/16,fd42::/48
          dns-servers: 10.43.0.53,fd43::53
          dns-domains: ~internal.example

      # Private TCP/UDP sockets use the gateway.
      - run: terraform apply -auto-approve

Usage

Configure private networks once.

Point proxy at your gateway and set audience to one of its --oidc-audience values. Grant the job id-token: write so it can mint its own token. Declaring an application lets policy scope rules to the tool you are running. Transparent mode additionally requires private CIDRs, DNS servers and routing domains. Include both address families when services publish A and AAAA records. These examples require the coordinated new client and Action release; older @v1 tags retain their previous behavior.

WHO

The job's identity

The runner's OIDC token carries the repository, workflow, and ref. The gateway verifies it; no secret is stored in CI.

WHAT

The application

The application input is sent as X-Masque-Application and matched by the policy's rules.

WHERE

Only allowed destinations

Each connection through the relay is a request the gateway evaluates. Anything no rule allows is denied.

How it works

Install, exchange, relay.

A Node 24 Action supervises the tunnel for the job and registers an always-running cleanup hook. Startup checks capabilities, authentication, listeners, routing and DNS before reporting readiness.

Install the client

Downloads skimasque-<version>-<target>.tar.gz and its .sha256 from the skimasque release, verifies the checksum and checks client capabilities. Transparent mode also installs a embedded tun-rs TUN support and a smoltcp-based stack. One client binary; no separate adapter download.

Open the tunnel

skimasque-client --github-oidc reads the runner's OIDC token, exchanges it at the gateway for a short-lived credential and renews it during the job. Both HTTP/HTTPS and SOCKS5 frontends share the authenticated session.

Egress through the gateway

Transparent mode routes configured private destinations and DNS through an owned TUN link, without global proxy variables. mode: proxy instead exports uppercase and lowercase HTTP, HTTPS, ALL and NO proxy variables for proxy-aware tools.

Supported runners

Linux, macOS, and Windows.

Transparent mode requires dedicated Ubuntu, TUN, iproute2, systemd-resolved, root or passwordless sudo, and no inherited HTTP/HTTPS/ALL proxy variables. Unsupported runners fail before network changes. Choose mode: proxy on Windows or macOS.

  • linux/amd64
  • linux/arm64
  • macos/arm64
  • windows/amd64
  • macos/amd64

Protocols

TCP and UDP through one relay.

Both modes support TCP and UDP; transparent mode supports private IPv4/IPv6 and DNS over either transport. ICMP is outside this interface. Transparent policy targets IP/CIDRs. The post hook removes owned state; unexpected tunnel failure blocks private routes until cleanup. Use ephemeral dedicated runners because forced host termination can prevent hooks. The gateway, the policy DSL, and the control plane live in skimasque-dev/skimasque.
